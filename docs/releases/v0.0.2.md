# Fjord OS v0.0.2 — Phase 2 Integration

## Release summary

`v0.0.2` is the first compiled Fjord release that completes the Phase 2
integration criterion. The kernel has been built for **x86_64** and **aarch64**.
It proves two isolated userspace task VSpaces, Tide priority/budget dispatch and
a task-aware endpoint IPC rendezvous in QEMU on both architectures.

> Successful boots emit `keel: PHASE2: IPC_ROUNDTRIP PASS (payload 0xf70dca11)`
> before the stable boot sentinel.

## Downloaded artifacts

The GitHub release contains the following generated files. Their exact SHA-256
values are in the accompanying `SHA256SUMS` file; validate every artifact before
booting it.

| File | Target | Purpose |
|---|---|---|
| `fjord-kernel-x86_64.elf` | x86_64 Fjord JSON target | PVH/QEMU kernel ELF |
| `fjord-kernel-aarch64.elf` | `aarch64-unknown-none-softfloat` | aarch64 `virt` kernel ELF |
| `fjord-kernel-aarch64.img` | aarch64 `virt` | flat binary image for QEMU/loaders |
| `SHA256SUMS` | all assets | SHA-256 integrity manifest |

On a host with `sha256sum`, verify the downloaded release directory as follows:

```sh
sha256sum --check SHA256SUMS
```

A successful verification prints `OK` for every listed file. A failed or missing
manifest check must be treated as a failed download; do not boot that artifact.

## Build provenance and reproducibility

The release is built from the annotated Git tag `v0.0.2` using the pinned Rust
`nightly-2026-06-01` toolchain, including `rust-src`, `rustfmt`, `clippy` and
`llvm-tools-preview`. The GitHub Actions release workflow compiles the same tag
for both targets and produces the aarch64 flat image using the toolchain's
`llvm-objcopy`.

The release build intentionally does **not** assert cryptographic publisher
signing. SHA-256 manifests provide transport-integrity checking only. Cask
signatures and Anchor/HSM-backed trust-anchor verification are still Phase 3
work; users must obtain release assets only from the Fjord GitHub release and
verify the tag/commit provenance independently.

## Highlights

| Area | Included in v0.0.2 |
|---|---|
| Task execution | TCB lifecycle, bound scheduling contexts, separate cloned CR3/TTBR0 roots and activate/restore guards |
| IPC | Synchronous endpoint queue with task-aware block/wake transitions |
| Userspace proof | Receiver → sender → awakened receiver round-trip across ring 3/EL0 and back |
| Tide | Bounded replenishment queue plus per-priority FIFO ready queues and a 256-bit ready bitmap |
| Memory integrity | W^X hardware mappings and streaming eager Cask Merkle verification with `O(log page_count)` state |
| Transparency gate | Domain-separated Logbook checkpoint message with mandatory fail-closed trust-anchor verifier interface |

## QEMU smoke commands

The repository includes the same runtime paths used by CI. They should reach the
Phase 2 IPC marker and then remain idle until the timeout stops QEMU.

```sh
# x86_64
cargo +nightly-2026-06-01 shipwright -- qemu

# aarch64
scripts/qemu-aarch64.sh -no-reboot
```

## Known limitations

This is a Phase 2 integration release, not a production security release. It
does not yet include hardware-backed measured boot, complete Ed25519/ML-DSA Cask
signatures, anti-rollback storage, a deployed append-only Logbook service,
disk encryption, or a general userspace service manager. The current Logbook
API requires a caller-provided checkpoint verifier and deliberately has no
permissive default implementation.
